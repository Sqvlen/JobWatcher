# Рейтинг компаній (не підключено)

Провайдера рейтингів **немає**. Рішення Задачі 14: законного способу отримувати рейтинг роботодавця автоматично, без партнерської угоди і без входу в акаунт замовника, я не знайшов. У `ServiceCollectionExtensions.cs` лишається `NullCompanyRatingProvider`: повідомлення про вакансію виходить без рейтингу, рядок `⭐ …` у ньому просто відсутній (ніколи не «N/A»). Специфікація це дозволяє («рейтинг, якщо вдасться знайти»). Налаштувань для рейтингів немає, бо нічого налаштовувати.

Це висновок із прочитаних документів, а не юридична консультація. Нижче сказано, що саме прочитано, що там написано, що я не міг прочитати і наскільки я впевнений.

## Правило рішення

Законний шлях існує **лише коли виконано всі три умови**: (1) сам сервіс публікує API чи стрічку, якою можна користуватися без особливого партнерства і без входу замовника; (2) його умови такого використання не забороняють; (3) відповідь справді містить рейтинг роботодавця. Якщо сумніви, то шляху немає. Те, що сторінки сервісу технічно можна скрапити, шляхом не вважається.

Як правило застосовано до доступу: реєстрація безкоштовного ключа розробника **допустима** (за цим правилом JobDataLake виконує умову 1), а вхід у особистий акаунт замовника (в сервісі, в Claude чи деінде) **ні**.

## Ризик зіставлення компанії

Навіть якби джерело знайшлося, вакансія дає лише **назву компанії як текст** (DOU: частина заголовка, Jooble: поле `company`, Djinni: для нових вакансій назва з блоку JSON-LD сторінки вакансії, `hiringOrganization.name`, а якщо сторінку прочитати не вдалося, «не вказано»). Ні домену сайту, ні ідентифікатора в жодному сервісі рейтингів ми не маємо. Тож будь-який пошук був би зіставленням за назвою: «Acme» проти «Acme Labs», «ТОВ Акме» проти «Акме», однойменні компанії різних країн, філії. Неправильний рейтинг гірший за відсутній, тому довелося б вимагати впевненого збігу і при сумніві мовчати. Це вторинна причина, але вона зменшує вигоду від будь-якого сумнівного джерела.

## Висновок

Серед прочитаного жоден із розглянутих сервісів не виконує всіх трьох умов правила. Для robota.ua це означає не «доведено, що не виконує», а «виконання не підтверджено» (портал API не прочитано), що за правилом дає той самий результат:

- Glassdoor, Indeed: рейтинг є, але офіційний доступ лише за схваленням, а автоматичний збір сторінок заборонено (за вторинними джерелами: умови Glassdoor і розділ D.3 умов Indeed не прочитано).
- Trustpilot: офіційний доступ лише за заявкою (умова 1), а TrustScore це оцінка споживачів, а не роботодавця (умова 3); умову 2 для API-клієнтів не прочитано.
- kununu, Comparably: рейтинг є на сайті, публічного API я не знайшов, автоматичний збір (за вторинними джерелами) заборонено.
- DOU: стрічку виставлено, але в ній лише тексти відгуків, без числа; доступ до сторінок із можливими числами підпадає під п. 2.5.
- Djinni: стрічка лише вакансій без назви компанії, джерела рейтингу не знайдено.
- Work.ua: публічного API з рейтингом не знайдено (відсутність знахідки, а не доказ відсутності); умови мовчать.
- robota.ua: API-портал існує (swagger), але нечитаний (403); чи є в ньому рейтинг роботодавця і що кажуть умови, не перевірено. Шляху не підтверджено.
- JobDataLake: API вільний і умови не проти, але рейтингу в профілі компанії немає.

Тому: **`NullCompanyRatingProvider` лишається, v1 виходить без рядка рейтингу.** Замінників я не вигадував: ні «рейтингу» з текстів відгуків, ні оцінки за сторонніми даними, ні «N/A».

**Впевненість.** Висока для кандидатів, у яких прочитано первинне джерело (Indeed, JobDataLake, DOU, Trustpilot), що законного автоматичного джерела рейтингу роботодавця серед розглянутих немає: для Indeed є первинне джерело (Developer Agreement: API лише за письмовим схваленням, для партнерів, агенцій і роботодавців); для JobDataLake і DOU є первинне джерело (документація, власне читання стрічки), що рейтингу в даних немає; для Trustpilot є документація з waitlist і споживчі умови. Для Glassdoor «немає відкритого API» підтверджено лише вторинно (офіційні сторінки дали 403). Для kununu і Comparably прочитано лише robots.txt (умови не прочитано, а відсутність публічного API це лише «не знайдено» за вебпошуком). Для Djinni і Work.ua сторінки компаній не відкривалися, а відсутність API лише не знайдена. Для цих п'яти кандидатів (Glassdoor, kununu, Comparably, Djinni, Work.ua), як і для robota.ua, висока впевненість не заявляється: результат тримається лише на правилі «якщо сумніви, то шляху немає», а не на прочитаному доказі. Помірна щодо окремих тверджень про умови Glassdoor, Indeed (розділ D.3), kununu і Comparably: їхні тексти я не прочитав і спираюся на вторинні уривки. Правило «якщо сумніви, то шляху немає» робить ці прогалини невідчутними для рішення: вони мали б значення лише тоді, коли б існував відкритий API, а серед прочитаного його немає. Для robota.ua там лише «не прочитано» (API-портал, див. нижче).

## Що могло б змінити рішення

- Glassdoor чи Indeed дали б замовнику письмове схвалення (партнерський доступ чи договір): тоді API стає законним, і треба буде реалізовувати провайдера.
- Замовник відкриває документацію robota.ua у браузері (`https://api.robota.ua/swagger/index.html` і сторінки умов robota.ua) і підтверджує, що там є відкритий для розробників API, який віддає рейтинг роботодавця, без партнерської угоди і без входу замовника в акаунт (реєстрація безкоштовного ключа розробника припустима), і що умови це дозволяють: тоді треба знову розглянути robota.ua як кандидата (читання таких сторінок замовником у власному браузері не порушує правила, бо програма нічого не обходить).
- **Indeed MCP-сервер** (інструмент `get_company_data` повертає оцінки роботодавця від співробітників; див. розділ про Indeed). Це найближчий офіційний машинний інтерфейс, що віддає рейтинг роботодавця. Чи можна викликати його поза сеансом Claude, з фонової програми, невідомо: його документація (`https://docs.indeed.com/mcp/`) віддала 403, а за вторинним зведенням вебпошуку сервер доступний лише як Claude Connector. Якщо Indeed підтвердить, що програма може користуватися ним без входу замовника в акаунт, і умови це дозволяють, його треба розглянути як кандидата.
- **Платні (комерційні) постачальники даних про роботодавців.** Їх не досліджували. Якщо замовник готовий платити, їх варто розглянути окремо за тими самими трьома умовами. Безкоштовний ключ розробника правило допускає (за ним розглянуто JobDataLake); вхід у акаунт замовника ні.
- DOU додало б числовий рейтинг до публічної стрічки (чи дало б згоду Адміністрації на читання сторінок компаній), або з'явився б інший сервіс, який публікує рейтинг роботодавця у відкритому API.
- Замовник захоче вести власний список «компанія → оцінка» у налаштуваннях. Це не джерело, а ручне введення; у проєкті його немає, і створювати без прохання замовника я не став.

## Як це працює в програмі

- `ServiceCollectionExtensions.cs` реєструє `NullCompanyRatingProvider` (його не змінювали): `GetAsync` повертає `null` для будь-якої компанії.
- `WatchCycle` усе ще викликає `ratings.GetAsync(vacancy.Company)` для кожної вакансії (без мережі, вартість нульова), отримує `null`, а `MessageFormatter` тоді опускає ` · ⭐ …`: рядок виглядає як «🏢 Компанія», без «N/A». Для вакансій Djinni це «🏢 не вказано».
- Якщо колись підключать справжнього провайдера, потрібне таке (у Задачі 14 не робилося, бо провайдера немає): (1) пропускати пошук для заглушки «не вказано» (`DjinniSource.UnknownCompany`; рядок «не вказано» сьогодні також продубльований у `MessageFormatter.NotSpecified`, тож константу варто перенести в одне місце, наприклад у `Domain`); (2) вимагати впевненого збігу назви (незалежно від регістру, розділових знаків і організаційно-правових форм, але «Acme» ≠ «Acme Labs»); (3) кешувати відповіді в пам'яті на час життя процесу; (4) не логувати ключі (за зразком `JoobleSource`).
