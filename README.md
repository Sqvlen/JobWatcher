# JobWatcher

Фоновий сервіс, який стежить за вакансіями і пише в Telegram **по одному повідомленню на кожну нову вакансію**, що підходить під ваш профіль: .NET, від 3 років досвіду, віддалено або Київ.

Інтерфейсу в нього немає: це .NET 10 worker без вебсторінок, а весь «інтерфейс» це повідомлення від вашого Telegram-бота. Налаштування лежать у `appsettings.json` і в змінних середовища, секрети (токен бота, ключі Jooble і JobsPipe) задаються змінними середовища або, за бажанням, беруться з Azure Key Vault (див. «Azure Key Vault»).

Як це працює:

1. Одразу після старту, а потім раз на 15 хвилин (налаштовується) сервіс читає увімкнені джерела: DOU і Djinni (типово), за бажанням Jooble і JobsPipe.
2. Усе, що вже було відоме, відкидається. Пам'ять про надіслане лежить у SQLite-файлі `seen.db` в каталозі даних.
3. Нове перевіряється фільтром профілю. Якщо вакансія підходить, ви отримуєте повідомлення в Telegram.
4. Збої не губляться мовчки: коли джерело чи весь цикл перевірки кілька разів поспіль не вдається, приходить окреме повідомлення (див. «Що ще приходить у Telegram»).

## Як виглядає повідомлення

Підписи українською, а вміст вакансії (назва, вимоги) мовою оригіналу, без перекладу й переказу:

```
🆕 Senior .NET Developer
🏢 Acme Corp
💰 $4000–5500
📍 Київ · Remote

📋 Вимоги:
• 5+ years of C#/.NET
• ASP.NET Core, PostgreSQL
• English B2+

🔗 Відкрити вакансію (DOU)
```

- Назва вакансії виділена жирним. Зарплата показується так, як її написав сайт, без перерахунків; якщо сайт її не вказує, буде `💰 не вказано`. Для Djinni зарплату сайт дає не текстом, а числами на сторінці вакансії, тож сервіс записує її в тому ж стилі, що й DOU (`$2000–2500`, `від $2000`, `до $2500`).
- Вимоги це до 4 пунктів, узятих дослівно з розділу вимог вакансії («Requirements», «Вимоги» тощо). Якщо чіткого розділу вимог немає, блоку `📋 Вимоги:` у повідомленні теж немає.
- Посилання веде на вакансію на сайті джерела, у дужках назва джерела: для DOU і Djinni це оригінальна вакансія на цьому сайті, для Jooble сторінка вакансії на самому Jooble (`link` з API), а не сайт роботодавця, а для JobsPipe оголошення на тому майданчику, звідки його взяв JobsPipe (Indeed, Himalayas тощо; у дужках стоїть «JobsPipe»). Jooble віддає лише короткий уривок опису, тож блоку вимог для нього зазвичай немає; JobsPipe дає повний текст, і вимоги, як правило, є.
- У затвердженому макеті є ще рядок із рейтингом компанії (`🏢 Acme Corp · ⭐ 4.2 (Glassdoor)`). **У цій версії рейтингу немає**: законного джерела для нього не знайшлося, тож цей фрагмент просто відсутній (див. «Джерела»). Також у v1 немає тега `Full-time` і періоду `/ міс` біля зарплати: зарплата показується рівно так, як її вказало джерело.
- Повідомлення не перевищує ліміт Telegram у 4096 символів: за потреби спершу прибираються останні пункти вимог, потім скорочується назва.

## Швидкий старт

Потрібен [.NET 10 SDK](https://dotnet.microsoft.com/download).

**1. Створіть бота.** У Telegram відкрийте [@BotFather](https://t.me/BotFather), надішліть `/newbot`, виберіть ім'я та username. BotFather відповість **токеном** виду `123456:ABC-DEF...`. Токен це пароль до бота.

**2. Дізнайтеся свій chat id.**

1. Знайдіть свого бота за username і надішліть йому будь-яке повідомлення (наприклад, `/start`). Поки ви першим не написали боту, він не може писати вам.
2. Відкрийте у браузері адресу, підставивши свій токен: `https://api.telegram.org/bot<ТОКЕН>/getUpdates`
3. У відповіді знайдіть `"message":{ ... "chat":{"id":123456789, ...}}`. Це число, `message.chat.id`, і є ваш chat id. Якщо `result` порожній, надішліть боту ще одне повідомлення й оновіть сторінку.

> **Токен ніде не публікуйте.** Адреса вище містить токен: не вставляйте її в чати, тікети, скриншоти чи інші відкриті місця, не показуйте на демо. Кожен, хто має токен, керує вашим ботом. Якщо токен потрапив комусь на очі, у @BotFather виконайте `/revoke` і отримайте новий.

Для групи: додайте бота в групу й надішліть там повідомлення, що звертається до бота (наприклад, `/start@username_бота`), після цього `getUpdates` покаже chat id групи (від'ємне число).

**3. Задайте токен і chat id змінними середовища.**

macOS / Linux (bash, zsh):

```bash
export JobWatcher__Telegram__BotToken='<токен>'
export JobWatcher__Telegram__ChatId='<chat id>'
```

Windows (PowerShell):

```powershell
$env:JobWatcher__Telegram__BotToken = '<токен>'
$env:JobWatcher__Telegram__ChatId = '<chat id>'
```

У Rider/Visual Studio те саме робиться в Run Configuration (Environment variables). Не записуйте токен у `appsettings.json`. Для хмари рекомендоване місце секретів це Azure Key Vault (див. «Azure Key Vault»).

**4. Запустіть.**

```bash
dotnet run --project src/JobWatcher
```

Якщо токена чи chat id немає, сервіс одразу завершується з кодом 1 і пояснює, що саме не задано (`Помилка конфігурації: ...`). Те саме в Docker: див. «Запуск у Docker».

**Перший запуск мовчазний, і це навмисно.** Сервіс не засипає чат десятками вакансій, які вже висять на сайтах: усе, що існує на момент першого запуску, тихо записується як «побачене», а повідомлення йдуть лише про **нові** вакансії, що з'явилися пізніше. Те, що все працює, видно в журналі:

```
info: JobWatcher.Watching.WatchCycle[0]
      First run of DOU: 25 existing vacancies marked as seen
```

Так само мовчазний «перший запуск» буде в кожного джерела, яке ви ввімкнете пізніше. Тож перше повідомлення прийде, лише коли на сайтах з'явиться нова вакансія, що підходить під профіль: можливо, доведеться почекати.

Каталог даних типово `./data`, відносно поточного (робочого) каталогу. За `dotnet run --project src/JobWatcher` це `src/JobWatcher/data/`. Змінити: `JobWatcher__DataDir`. А `appsettings.json` завжди береться з каталогу самої програми (поруч із `JobWatcher.dll`), хоч би з якого каталогу її запускали.

## Налаштування

Усі налаштування лежать у розділі `JobWatcher` файлу [`src/JobWatcher/appsettings.json`](src/JobWatcher/appsettings.json). Ось основне, що в ньому типово (розділ `Logging` опущено):

```json
{
  "JobWatcher": {
    "Telegram": { "BotToken": "", "ChatId": "" },
    "Profile": {
      "Keyword": ".NET",
      "Synonyms": [ "C#", "ASP.NET", "dotnet" ],
      "MinYearsExperience": 3,
      "Cities": [ "Київ", "Kyiv" ],
      "AllowedRemoteRegions": [ "Ukraine", "Europe", "EU", "Worldwide" ]
    },
    "Sources": {
      "Dou":      { "Enabled": true,  "FeedUrl": "https://jobs.dou.ua/vacancies/feeds/?category=.NET" },
      "Jooble":   { "Enabled": false, "ApiKey": "", "BaseUrl": "https://jooble.org/api" },
      "Djinni":   { "Enabled": true,  "FeedUrl": "https://djinni.co/jobs/rss/?primary_keyword=.NET",
                    "ReadVacancyPages": true, "PageRequestDelaySeconds": 2, "MaxPagesPerCycle": 15 },
      "JobsPipe": { "Enabled": false, "ApiKey": "", "BaseUrl": "https://api.jobspipe.dev", "ExcludedSources": [ "linkedin" ] },
      "LinkedIn": { "Enabled": false }
    }
  }
}
```

Крім цього, є налаштування, яких у файлі немає, бо їхні типові значення задані в коді (їх теж можна дописати у файл): `PollIntervalMinutes`, `MaxMessagesPerCycle`, `FailureAlertThreshold`, `DataDir`, `Profile:MinSalary`, `Sources:Jooble:MinFetchIntervalMinutes` і `Sources:JobsPipe:MinFetchIntervalMinutes`, `MaxAgeDays`, `PageSize`.

### Змінні середовища

Будь-яке налаштування можна перевизначити змінною середовища. Правило: шлях у конфігурації через `:` записується через **подвійне підкреслення** `__`, а на початку стоїть `JobWatcher`. Змінна має перевагу над файлом. Виняток один: адреса Azure Key Vault лежить в окремому розділі верхнього рівня, тож її змінна `KeyVault__VaultUri`, без `JobWatcher` (див. «Azure Key Vault»).

| Налаштування | Змінна середовища | Типово | Що робить |
|---|---|---|---|
| `Telegram:BotToken` | `JobWatcher__Telegram__BotToken` | порожньо, **обов'язково** | Токен бота від @BotFather. Секрет. |
| `Telegram:ChatId` | `JobWatcher__Telegram__ChatId` | порожньо, **обов'язково** | Куди слати повідомлення. |
| `PollIntervalMinutes` | `JobWatcher__PollIntervalMinutes` | `15` | Як часто опитувати джерела, у хвилинах (від 1 до 10080). Коли увімкнено DOU або Djinni, не менше **10**: DOU віддає стрічку з кешем на 10 хвилин (`Cache-Control: max-age=600`), тож частіше нічого не дає, а Djinni не оголошує інтервалу опитування, і її стрічка важить близько 270 КБ; опитувати їх частіше нечемно. Валідатор не пропустить менше. |
| `MaxMessagesPerCycle` | `JobWatcher__MaxMessagesPerCycle` | не задано (без ліміту) | Найбільше повідомлень за один цикл (не менше 1). Решта не губиться: ці вакансії лишаються непобаченими й підуть у наступних циклах. |
| `FailureAlertThreshold` | `JobWatcher__FailureAlertThreshold` | `3` | Після скількох невдалих опитувань одного джерела поспіль прийде повідомлення «джерело не відповідає», а після скількох невдалих циклів перевірки поспіль «цикл перевірки не вдається» (не менше 1). |
| `DataDir` | `JobWatcher__DataDir` | `./data` | Каталог, де лежить `seen.db`. У Docker-образі це `/app/data`. |
| `Profile:Keyword` | `JobWatcher__Profile__Keyword` | `.NET` | Головне слово пошуку. Не може бути порожнім. |
| `Profile:Synonyms` | `JobWatcher__Profile__Synonyms__0`, `__1`, ... | `C#`, `ASP.NET`, `dotnet` | Слова, які теж вважаються збігом з технологією. |
| `Profile:MinYearsExperience` | `JobWatcher__Profile__MinYearsExperience` | `3` | Мінімум років досвіду (не менше 0). |
| `Profile:Cities` | `JobWatcher__Profile__Cities__0`, `__1`, ... | `Київ`, `Kyiv` | Міста для не віддалених вакансій. |
| `Profile:AllowedRemoteRegions` | `JobWatcher__Profile__AllowedRemoteRegions__0`, ... | `Ukraine`, `Europe`, `EU`, `Worldwide` | Для яких регіонів віддалена вакансія вам підходить. |
| `Profile:MinSalary:Amount` | `JobWatcher__Profile__MinSalary__Amount` | не задано | Мінімальна зарплата (число більше 0). |
| `Profile:MinSalary:Currency` | `JobWatcher__Profile__MinSalary__Currency` | не задано | Код валюти. Сервіс розпізнає в зарплатах `USD`, `EUR`, `GBP`, `UAH` і `PLN`, тож беріть один із них. |
| `Profile:MinSalary:Period` | `JobWatcher__Profile__MinSalary__Period` | `Month` | `Month` (за місяць) або `Year` (за рік). |
| `Sources:Dou:Enabled` | `JobWatcher__Sources__Dou__Enabled` | `true` | Читати DOU. |
| `Sources:Dou:FeedUrl` | `JobWatcher__Sources__Dou__FeedUrl` | стрічка категорії .NET | Адреса RSS-стрічки DOU. |
| `Sources:Djinni:Enabled` | `JobWatcher__Sources__Djinni__Enabled` | `true` | Читати Djinni. |
| `Sources:Djinni:FeedUrl` | `JobWatcher__Sources__Djinni__FeedUrl` | стрічка за ключовим словом .NET | Адреса RSS-стрічки Djinni. |
| `Sources:Djinni:ReadVacancyPages` | `JobWatcher__Sources__Djinni__ReadVacancyPages` | `true` | Для кожної нової вакансії Djinni читати її публічну сторінку (лише машинний блок JSON-LD), щоб дізнатися компанію, зарплату, місце, формат роботи й роки досвіду. `false` повертає читання лише стрічки. |
| `Sources:Djinni:PageRequestDelaySeconds` | `JobWatcher__Sources__Djinni__PageRequestDelaySeconds` | `2` | Найменша пауза між двома запитами сторінок вакансій, у секундах (не менше 1). |
| `Sources:Djinni:MaxPagesPerCycle` | `JobWatcher__Sources__Djinni__MaxPagesPerCycle` | `15` | Найбільше сторінок вакансій за цикл (не менше 1). Решта нових вакансій чекає наступного циклу: їх не відкидають і не запам'ятовують, вони прийдуть пізніше. |
| `Sources:Jooble:Enabled` | `JobWatcher__Sources__Jooble__Enabled` | `false` | Читати Jooble (потрібен ключ). |
| `Sources:Jooble:ApiKey` | `JobWatcher__Sources__Jooble__ApiKey` | порожньо | Ключ Jooble. Секрет. Обов'язковий, коли Jooble увімкнено. |
| `Sources:Jooble:BaseUrl` | `JobWatcher__Sources__Jooble__BaseUrl` | `https://jooble.org/api` | Адреса API Jooble без ключа (лише `https`, без `?` і `#`). |
| `Sources:Jooble:MinFetchIntervalMinutes` | `JobWatcher__Sources__Jooble__MinFetchIntervalMinutes` | `720` | Найрідший інтервал між справжніми запитами до Jooble (див. нижче). |
| `Sources:JobsPipe:Enabled` | `JobWatcher__Sources__JobsPipe__Enabled` | `false` | Читати JobsPipe (потрібен ключ). |
| `Sources:JobsPipe:ApiKey` | `JobWatcher__Sources__JobsPipe__ApiKey` | порожньо | Ключ JobsPipe (`jp_live_...`). Секрет. Обов'язковий, коли JobsPipe увімкнено. |
| `Sources:JobsPipe:BaseUrl` | `JobWatcher__Sources__JobsPipe__BaseUrl` | `https://api.jobspipe.dev` | Адреса API JobsPipe (лише `https`, без `?` і `#`). |
| `Sources:JobsPipe:MinFetchIntervalMinutes` | `JobWatcher__Sources__JobsPipe__MinFetchIntervalMinutes` | `60` | Найрідший інтервал між справжніми запитами до JobsPipe (не менше 1; див. нижче). |
| `Sources:JobsPipe:MaxAgeDays` | `JobWatcher__Sources__JobsPipe__MaxAgeDays` | `14` | Запитуються вакансії, опубліковані не раніше ніж стільки днів тому (не менше 1). |
| `Sources:JobsPipe:PageSize` | `JobWatcher__Sources__JobsPipe__PageSize` | `25` | Скільки найновіших вакансій просити за один пошук (1–500; безкоштовний план обрізає до 25). |
| `Sources:JobsPipe:ExcludedSources` | `JobWatcher__Sources__JobsPipe__ExcludedSources__0` | `["linkedin"]` | Майданчики JobsPipe, вакансії яких пропускаються (назви як у JobsPipe: `linkedin`, `indeed`, `greenhouse`...). Список у змінних середовища задається індексами `__0`, `__1`... |
| `Sources:LinkedIn:Enabled` | `JobWatcher__Sources__LinkedIn__Enabled` | `false` | Лише показує повідомлення, що LinkedIn не підключено. |

Журнал іде в консоль (stdout). Його докладність змінюється звичайним способом .NET, наприклад `Logging__LogLevel__Default=Warning`.

### Як працює фільтр профілю

Вакансія відкидається лише тоді, коли джерело **прямо** каже, що вона не підходить. Якщо чогось не вказано, вакансія показується: краще зайве повідомлення, ніж пропущена вакансія.

- **Технологія**: ключове слово або будь-який синонім є в назві чи описі (без урахування регістру; після збігу не має одразу йти літера, тож `.NET Core` підходить, а `acme.network` ні).
- **Досвід**: відкидається, якщо джерело вказує менше `MinYearsExperience` років або в назві є junior/trainee/intern (та їхні українські відповідники). Роки читаються з назви й пунктів вимог. Якщо досвід не вказано, вакансія показується.
- **Місце**: для віддаленої вакансії підходить відсутність обмеження за регіоном або регіон зі списку `AllowedRemoteRegions` (віддалена лише для США не підійде). Для невіддаленої підходить місце, де є одне з `Cities`, або випадок, коли місце не вказано.
- **Зарплата** (лише коли задано `MinSalary`): вакансія відкидається, лише якщо найвища вказана сума явно менша за мінімум **у тій самій валюті**. Місяць і рік зіставляються (рік ділиться на 12), а ось **між валютами сервіс нічого не перераховує**: вакансія в іншій валюті, без зарплати, з відкритою верхньою межею («від $3000»), з погодинною ставкою чи незрозумілим періодом **показується**.

Приклад: не менше 3000 USD на місяць:

```bash
export JobWatcher__Profile__MinSalary__Amount=3000
export JobWatcher__Profile__MinSalary__Currency=USD
export JobWatcher__Profile__MinSalary__Period=Month
```

### Важливо: списки і змінні середовища

Списки (`Synonyms`, `Cities`, `AllowedRemoteRegions`), задані змінними середовища, **не замінюють** список із файлу, а накладаються на нього **за індексом**. Наприклад, `JobWatcher__Profile__Cities__0=Львів` дасть `Львів, Kyiv`: нульовий елемент замінено, решта лишилась зі списку у файлі. Дописати можна, якщо взяти наступний індекс (`JobWatcher__Profile__Synonyms__3=Blazor`). А прибрати чи повністю замінити список змінними не вийде.

**Щоб замінити список, відредагуйте `appsettings.json`.** У Docker після цього потрібно перебудувати образ (`docker build`). У `appsettings.json` не пишіть секретів: він потрапляє в образ. Секрети задавайте змінними середовища або в Azure Key Vault.

## Джерела

| Джерело | Типово | Як читається | Чесний стан |
|---|---|---|---|
| **DOU** | увімкнено | Офіційна RSS-стрічка категорії .NET, один запит на цикл | Працює. Компанія, зарплата (якщо є) і місце беруться із заголовка стрічки. |
| **Djinni** | увімкнено | Офіційна RSS-стрічка, один запит на цикл, плюс публічна сторінка кожної **нової** вакансії (лише блок JSON-LD, ≈2 сторінки на день) | Працює. У стрічці немає компанії, зарплати й місця; їх бере сторінка вакансії (рішення замовника, див. нижче). Якщо сторінку прочитати не вдалося, буде «не вказано». |
| **Jooble** | **вимкнено** | Офіційний REST API, потрібен ваш ключ | Не перевірено зі справжнім ключем. Дає лише уривок опису, тож вимог зазвичай немає. |
| **JobsPipe** | **вимкнено** | REST API, потрібен ваш ключ; зводить вакансії з багатьох майданчиків (Indeed, Himalayas, ATS компаній), повний текст | Перевірено зі справжнім ключем (2026-10-23): працює, але віддалених .NET-вакансій небагато, переважно США, **українських немає**. LinkedIn виключено, Indeed залишено на рішення замовника. |
| **LinkedIn** | **вимкнено** | Не підключено | Законного способу читати вакансії не знайдено. |
| Рейтинг компаній | немає | Немає | Законного джерела не знайдено, рядка `⭐` у повідомленні немає. |

### Тип джерела

У коді джерело вакансії задане переліком `VacancySource` з незмінними числами; у повідомленні показується назва сайту з другого стовпця.

| Число | Значення | Назва в повідомленні |
|---|---|---|
| 1 | `Dou` | DOU |
| 2 | `Djinni` | Djinni |
| 3 | `Jooble` | Jooble |
| 4 | `LinkedIn` | LinkedIn |
| 5 | `JobsPipe` | JobsPipe |

Числа зберігаються в `seen.db` і не змінюються (нові джерела лише дописуються в кінець). Після оновлення зі старої версії, яка зберігала назву джерела текстом, наявний `data/seen.db` ігнорується: кожне джерело один раз тихо запам'ятає наявні вакансії, як під час першого запуску. Видаліть `data/seen.db`, якщо хочете чистий старт.

### DOU

Читається лише RSS-стрічка `https://jobs.dou.ua/vacancies/feeds/?category=.NET`, яку DOU сама публікує (кнопка «RSS» на сторінці вакансій). Явної згоди DOU на її автоматичне читання немає: див. «Про законність читання». Один запит на цикл, без повторів. Для іншої категорії змініть `category=` в `FeedUrl`, але врахуйте: **зміна адреси стрічки не є «першим запуском»**. У базі вже є id цього джерела, тож мовчазного запам'ятовування не буде, і всі ще не бачені вакансії нової стрічки, що підходять під профіль, прийдуть повідомленнями одразу (у межах `MaxMessagesPerCycle`, якщо його задано). Подробиці, умови й формат стрічки: [docs/sources/dou.md](docs/sources/dou.md).

### Djinni

Читається офіційна RSS-стрічка `https://djinni.co/jobs/rss/?primary_keyword=.NET`, а для кожної **нової** вакансії ще й її публічна сторінка. Що з цього випливає, чесно:

- У стрічці **немає компанії, зарплати й місця**. Тому для кожної нової вакансії сервіс робить один анонімний запит її сторінки й читає звідти лише машинний блок JSON-LD (дані schema.org `JobPosting`, які Djinni сама публікує для пошуковиків): компанію, зарплату, формат роботи (віддалено чи офіс), місто офісу, для віддаленої роботи країну чи регіон кандидата, а також роки досвіду. Перший запуск сторінок не читає. Сторінки читаються по черзі, щонайменше за 2 секунди одна від одної й від запиту стрічки, не більше 15 за цикл (решта нових вакансій чекає наступного циклу); перенаправлення не виконуються, а сторінку кожної вакансії читають один раз, навіть якщо надіслати її вдається не одразу. За типового профілю це приблизно 2 сторінки на день.
- Завдяки цьому фільтр профілю працює для Djinni так само, як для DOU: офісна вакансія з іншого міста, віддалена лише для країни поза `AllowedRemoteRegions` чи із зарплатою нижче `MinSalary` відсіюється. Якщо сторінку прочитати не вдалося (помилка, сторінка без цих даних), вакансія приходить як раніше: `🏢 не вказано`, `💰 не вказано`, без рядка місця, і за місцем, форматом та зарплатою не відсіюється (лише за технологією, junior у назві та роками з вимог).
- Читання сторінок виходить за межі «лише офіційна стрічка»: це рішення замовника, див. «Про законність читання». Вимкнути його можна `JobWatcher__Sources__Djinni__ReadVacancyPages=false`.
- Звузити пошук можна на боці Djinni: відкрийте https://djinni.co/jobs/, виставте фільтри (місто, віддалено, рівень), візьміть адресу посилання «Стрічка вакансій в RSS» і задайте її в `JobWatcher__Sources__Djinni__FeedUrl` (як і для DOU, зміна адреси стрічки не є «першим запуском»: усі ще не бачені підхожі вакансії нової стрічки прийдуть одразу). Але одна стрічка, імовірно, не вміє «віддалено **або** Київ»: фільтри Djinni, судячи з перевірки, складаються як «і» (AND), а перевірено лише одну комбінацію, `location=kyiv&employment=remote&region=UKR` (вона дала 1 вакансію проти 59 без фільтрів). Тож порада «виставте місто й віддалено» буквально приховала б більшість підхожих вакансій, і доведеться вибрати одне. Підтримка двох адрес стрічок була б майбутнім варіантом. Кожен фільтр окремо й решту фільтрів сторінки не перевіряли.
- Якщо Djinni вам не підходить, вимкніть її: `JobWatcher__Sources__Djinni__Enabled=false`.

Подробиці: [docs/sources/djinni.md](docs/sources/djinni.md).

### Jooble (вимкнено типово)

Jooble дає офіційний REST API, але **ключ потрібно отримати самому**: для України заявка на https://ua.jooble.org/api/about (безкоштовно). Ключ з `jooble.org`, за довідкою Jooble, дає доступ лише до вакансій США. Увімкнення:

```bash
export JobWatcher__Sources__Jooble__Enabled=true
export JobWatcher__Sources__Jooble__ApiKey='<ключ>'
```

На що зважити:

- **Домен ключа.** Ключ діє лише на тому домені Jooble, де його видано. Український ключ, імовірно, вимагає ще й `JobWatcher__Sources__Jooble__BaseUrl=https://ua.jooble.org/api` (**перевірте зі справжнім ключем**: без ключа це підтвердити не вийшло).
- **Квота.** Безкоштовний ключ має ліміт приблизно **500 запитів за весь час життя** ключа (не на місяць). Одна вибірка це 2 запити (перше місто профілю, `Profile:Cities[0]`, і `remote`), тому сервіс сам обмежує справжні запити: `MinFetchIntervalMinutes` типово **720** (раз на 12 годин), що дає ключу близько 125 діб. Якщо поставити 60, ключ вичерпається приблизно за 10 діб. Перезапуски процесу теж роблять запит одразу, тож часті перезапуски витрачають квоту.
- **Що не підтверджено.** Тестові відповіді Jooble у проєкті **синтетичні** (ключа на момент написання не було), тож перевірка адаптера зі справжнім ключем лишається відкритою. Зокрема значення `location: "remote"`, яким адаптер шукає віддалену роботу, у документації Jooble не згадане, і чи дає воно віддалені вакансії, невідомо. Умови «Jooble API Terms of Use» знайти не вдалося.

Подробиці й чекліст перевірки: [docs/sources/jooble.md](docs/sources/jooble.md).

### JobsPipe (вимкнено типово)

JobsPipe збирає вакансії з багатьох майданчиків і віддає їх через REST API разом з **повним текстом** оголошення, тож блок `📋 Вимоги:` для його вакансій, як правило, є (у перевірці 2026-10-23 вимоги знайшлися у 7 із 10 справжніх описів). **Ключ потрібно отримати самому**: https://jobspipe.dev/signup (безкоштовно, один акаунт). Увімкнення:

```bash
export JobWatcher__Sources__JobsPipe__Enabled=true
export JobWatcher__Sources__JobsPipe__ApiKey='<ключ>'
```

або секрет `JobWatcher--Sources--JobsPipe--ApiKey` в Azure Key Vault. На що зважити:

- **Що саме шукається.** Один запит за вибірку: віддалені вакансії, у назві яких є ключове слово профілю чи синонім, за останні `MaxAgeDays` (14) днів, до `PageSize` (25) найновіших. Київ не шукається: українських майданчиків у JobsPipe немає, а перевірка 2026-10-23 за країною UA й локацією «Ukraine/Kyiv» дала нуль вакансій.
- **Країна віддаленої вакансії.** JobsPipe називає країну, де вакансія «сидить». UA, US, GB і країни Європи зіставляються з регіонами `AllowedRemoteRegions` (`Ukraine`, `US`, `UK`, `EU`, `Europe`), а **будь-яка інша країна відсіюється**, якщо її не додано до цього списку (віддалена вакансія, прив'язана до Індії чи Австралії, вам не потрібна). Типовий список не містить `US` і `UK`: додайте їх, якщо хочете віддалену роботу, прив'язану до цих країн.
- **Indeed і LinkedIn.** JobsPipe називає серед зібраних майданчиків LinkedIn і Indeed, але спосіб збору не вказує. LinkedIn виключено типово (`ExcludedSources`). **Indeed залишено на явне рішення замовника (2026-10-23)**; щоб прибрати, додайте `indeed` до `ExcludedSources`. Українські вакансії Indeed через JobsPipe недоступні.
- **Квота.** Безкоштовний ключ дає 1000 кредитів (чи це разово, чи щомісяця, не підтверджено). Кредит це одна вакансія, якої ключ цього місяця ще не отримував: повторно віддані вакансії безкоштовні, пошук без результатів теж. Окрім цього є місячна квота запитів, тому справжній запит робиться не частіше ніж раз на `MinFetchIntervalMinutes` (60); усередині інтервалу виклик не робить запиту, а після невдалого запиту повторює ту саму помилку, щоб сигнал «джерело не відповідає» спрацював. Перезапуск процесу робить запит одразу.
- **Умови.** Політика JobsPipe дозволяє «job alerts that send applicants to the original posting» і вимагає лишати посилання на оригінал (сервіс шле його без змін), забороняє кілька безкоштовних акаунтів і збирання контактів.

Подробиці, поля й результати перевірки: [docs/sources/jobspipe.md](docs/sources/jobspipe.md).

### LinkedIn (вимкнено, не підключено)

Адаптера **немає**. Відкритого API для читання вакансій LinkedIn не пропонує: продукти, пов'язані з вакансіями, призначені для розміщення вакансій і доступні лише схваленим партнерам. Публічної RSS-стрічки в документації немає. Угода користувача LinkedIn забороняє скрапінг й автоматичний доступ і діє також для відвідувачів без акаунта, а `robots.txt` закриває LinkedIn для будь-якого не названого в ньому робота (`User-agent: *` / `Disallow: /`). Єдина офіційна функція (Job alerts) прив'язана до вашого акаунта й пошти. Тому вакансії LinkedIn сервіс не читає.

Якщо ввімкнути `JobWatcher__Sources__LinkedIn__Enabled=true`, нічого не шукатиметься: сервіс лише раз за запуск надішле в Telegram повідомлення «ℹ️ Джерело LinkedIn не підключено: ...». Натомість можна самому налаштувати Job alerts у LinkedIn (листи на пошту). Подробиці: [docs/sources/linkedin.md](docs/sources/linkedin.md).

### Рейтинг компаній

Не реалізовано. Серед Glassdoor, Indeed, Trustpilot, kununu, Comparably, відгуків DOU та інших не знайшлося джерела, яке одночасно було б відкритим для програм, не заборонялося умовами й справді віддавало б рейтинг роботодавця (для robota.ua документацію прочитати не вдалося, а сторінок компаній Work.ua і Djinni не відкривали, тож для них шлях не підтверджено; за правилом «якщо сумніви, то шляху немає» рішення те саме). Вигадувати рейтинг сервіс не став: рядка з ним у повідомленні просто немає (ніколи не «N/A»). Подробиці: [docs/sources/ratings.md](docs/sources/ratings.md).

### Про законність читання

Коротко й без прикрас, це **міркування автора, а не юридична консультація**:

- Умови DOU (п. 2.5) забороняють автоматизований доступ до сайту, зокрема автоматичне збирання інформації, «без згоди Адміністрації»; про RSS-стрічки вони нічого не кажуть. **Явної згоди немає**: ми лише виводимо її з того, що DOU сама публікує стрічку (кнопка «RSS» на сторінці вакансій, тип `application/rss+xml`, `Cache-Control: max-age=600`, мітка `utm_source=jobsrss` у посиланнях). Це судження автора, а не дозвіл; на HTML-сторінки воно не поширюється.
- Умови Djinni про автоматичний доступ і про стрічку **мовчать**: ні дозволу, ні заборони. Стрічку публікує сама Djinni.
- Адаптери читають ці офіційні RSS-стрічки (Jooble: лише офіційне API зі своїм ключем). Вони не входять в акаунти й нічого не обходять; DOU і Djinni отримують по одному запиту стрічки на цикл, і сервіс називається в `User-Agent`. **Виняток, на явне рішення замовника (2026-10-22): Djinni.** Для кожної нової вакансії Djinni сервіс читає її публічну сторінку, але лише блок JSON-LD (`JobPosting`), який Djinni сама додає для роботів: анонімно, з тим самим `User-Agent` (`JobWatcher/1.0 (personal job alerts; reads the public Djinni RSS feed and the pages of new vacancies)`), без cookie, лише адреси на `djinni.co`, перенаправлення не виконуються, з паузою між запитами й лімітом за цикл, і кожну сторінку один раз (поки вакансія чекає надсилання, прочитане береться з пам'яті). robots.txt Djinni (перевірено 2026-10-22) забороняє лише `/jobs2` та кілька інших розділів, а не `/jobs/<номер>-...`; умови про автоматичний доступ мовчать. Це судження автора й рішення замовника, а не дозвіл Djinni і не юридична консультація, і воно виходить за межі правила «лише офіційні стрічки». Сторінки DOU сервіс не читає. Кожне повідомлення містить незмінене посилання на вакансію на сайті джерела (для Jooble це сторінка вакансії на самому Jooble).
- JobsPipe (вимкнено типово) не сайт вакансій, а комерційний API-посередник, який збирає чужі оголошення. Сервіс користується лише його API за його умовами (ключ, ліміти, посилання на оригінал). Як сам JobsPipe збирає Indeed і LinkedIn, він не каже; LinkedIn виключено, а Indeed залишено на рішення замовника (2026-10-23). Це судження автора й замовника, а не юридична консультація. Деталі: [docs/sources/jobspipe.md](docs/sources/jobspipe.md).
- Використання особисте й некомерційне: одна людина, повідомлення у її власний Telegram.
- Якщо вам потрібна певність, напишіть сайтам. Якщо сайт заперечуватиме, вимкніть джерело: `JobWatcher__Sources__Dou__Enabled=false` або `JobWatcher__Sources__Djinni__Enabled=false` (або лише читання сторінок Djinni: `JobWatcher__Sources__Djinni__ReadVacancyPages=false`). Хоч одне джерело має лишитися увімкненим, інакше сервіс не стартує.

## Запуск у Docker

Знати Docker докладно не потрібно: образ збирається одним рядком, а запускається однією командою.

**Зібрати образ** (з кореня проєкту):

```bash
docker build -t jobwatcher .
```

**Запустити** зі змінними середовища і томом для даних:

```bash
docker run -d --name jobwatcher --restart unless-stopped \
  -e JobWatcher__Telegram__BotToken='<токен>' \
  -e JobWatcher__Telegram__ChatId='<chat id>' \
  -v jobwatcher-data:/app/data \
  jobwatcher
```

- `-d` запускає у фоні, `--restart unless-stopped` піднімає сервіс після перезавантаження Docker чи комп'ютера.
- `-v jobwatcher-data:/app/data` це **іменований том**: Docker сам створить його й збереже між перезапусками та оновленнями контейнера. Там лежить `seen.db`. Без тома база пропадає разом із контейнером (див. «Перенесення в хмару»).
- Образ не містить жодних секретів: токен і ключі передаються лише під час запуску (змінними середовища або з Azure Key Vault, див. «Azure Key Vault»). Сервіс працює від непривілейованого користувача (не root).
- Забули токен чи chat id? Контейнер одразу завершиться з кодом 1 і поясненням `Помилка конфігурації: ...` (його видно в `docker logs jobwatcher`). З `--restart unless-stopped` Docker тоді перезапускатиме його знову й знову, доки ви не виправите змінні.

**Змінні з файлу.** Щоб не писати токен у командному рядку, покладіть змінні у файл `jobwatcher.env` (по одній `ІМ'Я=значення` на рядок, **без лапок**, цей файл нікуди не публікуйте):

```
JobWatcher__Telegram__BotToken=123456:ABC-DEF...
JobWatcher__Telegram__ChatId=123456789
JobWatcher__PollIntervalMinutes=30
```

```bash
docker run -d --name jobwatcher --restart unless-stopped \
  --env-file jobwatcher.env \
  -v jobwatcher-data:/app/data \
  jobwatcher
```

**Щоденні команди:**

```bash
docker logs -f jobwatcher          # дивитися журнал (Ctrl+C виходить, сервіс лишається)
docker stop jobwatcher             # зупинити (сервіс завершується коректно, код виходу 0)
docker start jobwatcher            # запустити знову, дані на місці
docker rm -f jobwatcher            # видалити контейнер (том із даними лишається)
```

**Змінили налаштування чи код?** Змінні задаються під час створення контейнера, тому: `docker rm -f jobwatcher`, за потреби `docker build -t jobwatcher .`, і знову `docker run ...` із тим самим томом. Джерела читаються на старті, тож без перезапуску зміни не підхопляться.

**Попередження про каталог замість тома.** Замість іменованого тома можна змонтувати каталог хоста (`-v /шлях/data:/app/data`), але сервіс працює від користувача з id **1654**, тож каталог має бути доступний йому на запис (`chown 1654 /шлях/data`). З іменованим томом цього робити не треба.

## Перенесення в хмару

Образ готовий до цього: секрети йдуть зі змінних середовища або з Azure Key Vault, дані з тома. Але є три речі, які не можна пропустити.

1. **Постійний том для `/app/data` обов'язковий.** Без нього після кожного перезапуску чи повторного розгортання `seen.db` порожня, і сервіс знову проходить мовчазний «перший запуск»: усе, що з'явилося за час простою, мовчки позначається побаченим і **до вас не дійде**. Підключіть до `/app/data` постійне сховище платформи (volume, persistent disk). Запускайте рівно **один** екземпляр: у кожного свої дані, і два екземпляри слатимуть вам однакові повідомлення.

   Том платформи має бути **доступний на запис користувачу з id 1654**, від якого працює сервіс (наприклад, у Kubernetes це `securityContext: { fsGroup: 1654 }` у специфікації пода). Інакше кожен цикл завершується помилкою збереження даних. Вона записується в журнал (`Watch cycle failed`), процес продовжує працювати, але вакансії не надходять; після `FailureAlertThreshold` таких циклів поспіль (типово 3) у Telegram приходить «⚠️ Цикл перевірки не вдається ...» (див. «Що ще приходить у Telegram»). Тому після першого розгортання все одно перегляньте журнал.
2. **Секрети лише через сховище секретів.** В Azure рекомендоване місце це Azure Key Vault з managed identity (див. «Azure Key Vault»): тоді жоден секрет не стоїть у змінних середовища. На інших платформах передавайте токен бота й ключі Jooble та JobsPipe як секретні змінні середовища (`JobWatcher__Telegram__BotToken` та ін.). В образ чи файли їх не вшивайте.
3. **Зовнішній heartbeat потрібен.** Сервіс сам повідомляє про несправність джерел і про цикли перевірки, що раз у раз не вдаються, але **не вміє повідомити про власну зупинку**: якщо процес чи машина вимкнені, надсилати повідомлення про це нікому. Локально з цим доводиться миритися, а в хмарі налаштуйте зовнішню перевірку: сповіщення платформи про зупинку/перезапуски контейнера, uptime-монітор чи свій регулярний пінг. Вбудованого heartbeat у цій версії немає: сервіс не відкриває HTTP-портів і нічого нікуди не пінгує.

Сама зупинка вакансій не губить: нове визначається за збереженими id, а не за часом, тож після відновлення сервіс підхоплює те, що з'явилося за час простою, за умови, що том збережено. Межа одна: у стрічках лише найновіші вакансії (DOU віддає 25, Djinni 59), тож за дуже довгий простій найстаріші можуть вже з них випасти.

## Azure Key Vault

Секрети (токен бота, chat id, ключі Jooble і JobsPipe) можна тримати в [Azure Key Vault](https://learn.microsoft.com/azure/key-vault/) замість змінних середовища. Механізм той самий, що в інших наших сервісах: розділ `KeyVault` з адресою сховища, вхід через `DefaultAzureCredential`. Відмінність одна: сервіс бере лише **свої** секрети, ті, чия назва починається з `JobWatcher--`.

**Що це дає, а що ні.** Справжня користь в Azure: контейнер із **managed identity** читає секрети сам, і жоден секрет не стоїть ні в змінних середовища, ні в образі, ні у файлах. Локально чи в Docker поза Azure сервісу однаково потрібен спосіб увійти в Azure: на своєму комп'ютері це ваш `az login`, а в контейнері змінні service principal (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_CLIENT_SECRET`), тобто знову секрет у змінній середовища. Тож поза Azure Key Vault зручний, щоб усі секрети лежали в одному місці, але змінних середовища не позбавляє.

**Як увімкнути.** Задайте адресу сховища (вона у властивостях сховища на порталі Azure, «Vault URI»):

```bash
export KeyVault__VaultUri='https://<name>.vault.azure.net/'
```

або в локальному файлі налаштувань (наприклад, `appsettings.Development.json`, який читається при `DOTNET_ENVIRONMENT=Development`):

```json
{ "KeyVault": { "VaultUri": "https://<name>.vault.azure.net/" } }
```

Адреса має бути повною і з `https`. Порожня адреса (так у `appsettings.json` типово) означає «Key Vault вимкнено»: сервіс до Azure не звертається взагалі.

**Назви секретів.** Шлях налаштування записується через `--` замість `:` і з префіксом `JobWatcher--`:

| Секрет у Key Vault | Налаштування | Змінна середовища, яку він заміняє |
|---|---|---|
| `JobWatcher--Telegram--BotToken` | `JobWatcher:Telegram:BotToken` | `JobWatcher__Telegram__BotToken` |
| `JobWatcher--Telegram--ChatId` | `JobWatcher:Telegram:ChatId` | `JobWatcher__Telegram__ChatId` |
| `JobWatcher--Sources--Jooble--ApiKey` | `JobWatcher:Sources:Jooble:ApiKey` | `JobWatcher__Sources__Jooble__ApiKey` |

Так само можна задати будь-яке інше налаштування (наприклад, `JobWatcher--PollIntervalMinutes`), а елемент списку через його індекс: `JobWatcher--Profile--AllowedRemoteRegions--0` (накладається за індексом, як і змінні середовища, див. «Важливо: списки і змінні середовища»). Префікс не залежить від регістру. Вимкнені (disabled) секрети пропускаються.

Створити секрет:

```bash
az keyvault secret set --vault-name <vault> --name JobWatcher--Telegram--BotToken --value '<токен>'
```

**Чому префікс.** Сховище може бути спільним з іншими застосунками. Сервіс бачить список назв усіх секретів (для цього потрібен дозвіл List), але **значення** читає лише тих, що починаються з `JobWatcher--`; значення чужих секретів він не запитує і в налаштування не бере.

**Права.** Ідентичність, від якої працює сервіс (managed identity, service principal або ваш обліковий запис при `az login`), має мати право читати секрети: для сховища з Azure RBAC це роль **Key Vault Secrets User**, для сховища з access policies це політика з дозволами секретів **Get** і **List**. Роль призначайте на рівні сховища, а не окремих секретів: сервісу потрібен перелік секретів сховища. Роль «Key Vault Secrets User» уже містить і читання значень, і перелік (readMetadata). Документація пакета `Azure.Extensions.AspNetCore.Configuration.Secrets` згадує ще й «Key Vault Reader»: спершу спробуйте без неї (вона дає ще й метадані ключів і сертифікатів). Точні назви ролей і дозволів перевірте в документації Azure.

**Хто може писати секрети, той може змінити й налаштування.** Будь-який секрет `JobWatcher--…` перекриває налаштування, а не лише секрети: наприклад, `JobWatcher--Sources--Jooble--BaseUrl` відправив би ключ Jooble на інший сервер. Тож право запису в сховище давайте якомога вужчому колу.

**Що має перевагу.** `appsettings.json` < `appsettings.Development.json` < змінні середовища < аргументи командного рядка < Key Vault. Тобто секрет зі сховища перекриває однойменну змінну середовища і навіть аргумент командного рядка.

**Вхід.** Використовується `DefaultAzureCredential`: він по черзі пробує змінні service principal, managed identity, вхід Azure CLI (`az login`) тощо (повний порядок перевірте в документації Azure). Локально (коли `DOTNET_ENVIRONMENT=Development` або `IS_LOCAL=1`) managed identity пропускається, як і в інших наших сервісах: достатньо `az login`.

**Як вимкнути.** `KeyVault__VaultUri=""` (або просто не задавати адресу).

**Старт.** Коли адресу задано, сервіс перед читанням сховища пише в консоль один рядок `Читаю секрети з Azure Key Vault…` (без адреси й назв секретів). Якщо сховище не відповідає, кожен запит до нього обривається через 20 секунд і повторюється щонайбільше двічі (з короткими паузами), тож мовчазне очікування обмежене: у найгіршому разі близько хвилини, після чого буде `Помилка Azure Key Vault:`.

**Зміна секрету.** Секрети читаються **один раз, на старті**. Змінили чи ротували секрет у сховищі: перезапустіть сервіс.

**Docker і хмара.** Dockerfile змінювати не треба: Azure SDK сам читає змінні середовища. У контейнері поза Azure:

```bash
docker run -d --name jobwatcher --restart unless-stopped \
  -e KeyVault__VaultUri='https://<name>.vault.azure.net/' \
  -e AZURE_TENANT_ID='<tenant id>' \
  -e AZURE_CLIENT_ID='<client id>' \
  -e AZURE_CLIENT_SECRET='<client secret>' \
  -v jobwatcher-data:/app/data \
  jobwatcher
```

В Azure (наприклад, Container Apps чи App Service) увімкніть контейнеру managed identity, дайте їй права на сховище (див. «Права») і задайте лише `KeyVault__VaultUri`. Для user-assigned identity, ймовірно, треба ще `AZURE_CLIENT_ID` з її client id: перевірте в документації Azure.

**Якщо не вдається.** Коли адреса задана, а секрети прочитати не вдалося (неправильна адреса, немає входу, немає прав, сховище недоступне), сервіс **не стартує** і завершується з кодом 1:

```
Помилка Azure Key Vault:
- CredentialUnavailableException: DefaultAzureCredential failed to retrieve a token from the included credentials.
Перевірте VaultUri, доступ (роль «Key Vault Secrets User» або політика Get+List) і вхід (`az login` для локального запуску; managed identity або AZURE_CLIENT_ID/AZURE_TENANT_ID/AZURE_CLIENT_SECRET для контейнера)
```

У другому рядку тип помилки й перший рядок її тексту (без значень секретів). Найчастіше:

- `UriFormatException`: `KeyVault__VaultUri` не повна адреса з `https://`.
- `CredentialUnavailableException` або `AuthenticationFailedException`: немає входу. Локально виконайте `az login`; у контейнері перевірте змінні `AZURE_*` чи managed identity.
- `RequestFailedException (403): ...` (або `(401)`): вхід є, але немає прав на секрети (див. «Права»). Код HTTP-статусу стоїть у дужках після типу помилки.
- `RequestFailedException (404): ...`: за цією адресою сховища немає, перевірте `KeyVault__VaultUri`.
- `RequestFailedException` без статусу чи помилка мережі/таймауту: сховище недоступне або адреса вказує не туди. Перед помилкою SDK робить повторні спроби (див. «Старт»), тож це може зайняти близько хвилини.

Якщо ж сховище прочитано, але в ньому немає потрібного секрету, сервіс завершиться звичайною `Помилка конфігурації: ...`, де названо і змінну, і секрет Key Vault.

## Розгортання на DigitalOcean (покроково)

Перевірений приклад (жовтень 2026): один маленький Droplet, секрети в Azure Key Vault. Він доповнює розділи «Перенесення в хмару» й «Azure Key Vault», а не замінює їх. Ціни й вигляд сторінок DigitalOcean та Azure змінюються, тож звіряйте їх на місці. Усі `<…>` це ваші значення; справжні IP, ідентифікатори й секрети в README не записуйте.

**Розмір.** Droplet Basic, Regular (shared CPU), приблизно **$4 на місяць**: 1 vCPU, 512 МіБ RAM, диск 10 ГіБ, Ubuntu 24.04 LTS x64, регіон Amsterdam. Сервіс легкий: у тесті Docker (ліміт 256 МіБ) контейнер займав 36 МіБ на старті, 47–48 МіБ далі, пік за cgroup 50 МіБ (RSS процесу 106 МБ, разом із файлами runtime), CPU близько 0,2% одного ядра. На самому сервері після Docker було використано близько 180 МіБ із 458 МіБ, доступно ≈ 276 МіБ. Тест не охоплював цикл із новими вакансіями Djinni (читання сторінок), тож через кілька діб перевірте пік уже на сервері: `docker exec jobwatcher cat /sys/fs/cgroup/memory.peak`.

### 1. Droplet і SSH-ключ

У формі створення Droplet: образ **Ubuntu 24.04 (LTS) x64**, тариф **Basic → Regular** (найдешевший), **Public IPv4** увімкнути, IPv6, Backups, Volumes і Startup scripts не потрібні, автентифікація **SSH Keys**, ім'я `jobwatcher`.

Ключ створіть окремий для цього сервера, **із парольною фразою**:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/jobwatcher_digitalocean -C "jobwatcher droplet, digitalocean"
ssh-add --apple-use-keychain ~/.ssh/jobwatcher_digitalocean   # macOS: запам'ятати фразу
```

У DigitalOcean вставте лише **відкритий** ключ (`~/.ssh/jobwatcher_digitalocean.pub`), приватний нікуди не передавайте. Фразу збережіть у менеджері паролів: відновити її неможливо, при втраті доведеться створити новий ключ і дописати його в `authorized_keys` на сервері.

### 2. Налаштування сервера

Перший вхід: `ssh -i ~/.ssh/jobwatcher_digitalocean root@<IP-адреса>`. Далі під `root`:

```bash
apt update && apt upgrade -y
```

Якщо `apt` запитає про `sshd_config`, оберіть **«keep the local version currently installed»** (за замовчуванням підсвічено перезапис, його обирати не треба). Якщо після оновлення існує `/var/run/reboot-required`, виконайте `reboot` і зайдіть знову.

Свап 1 ГБ як запас пам'яті (спершу `free -h`: якщо `Swap` уже не `0B`, пропустіть):

```bash
fallocate -l 1G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab    # обов'язково >>, один > затре файл
```

Окремий користувач замість `root`:

```bash
adduser deploy
usermod -aG sudo deploy
mkdir -p /home/deploy/.ssh
cp /root/.ssh/authorized_keys /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh
chmod 700 /home/deploy/.ssh && chmod 600 /home/deploy/.ssh/authorized_keys
```

**Перевірте вхід у новій вкладці, не закриваючи сесію `root`:** `ssh -i ~/.ssh/jobwatcher_digitalocean deploy@<IP-адреса>`, потім `sudo whoami` (має бути `root`). Лише після цього закрийте вхід під `root` і за паролем. Далі вже від `deploy`:

```bash
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf > /dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowUsers deploy
EOF
sudo sshd -t && sudo systemctl reload ssh
```

Ім'я файлу починається з `00`: SSH читає файли за абеткою і для кожного параметра бере перше значення, тож ці правила перемагають налаштування cloud-init. Перевірка: `sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|allowusers) '`, а вхід під `root` має давати `Permission denied (publickey)`.

Файрвол (порт SSH дозвольте **до** `enable`, інакше втратите доступ):

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw enable
sudo ufw status verbose
```

Сервісу вхідні порти не потрібні, він лише читає джерела й пише в Telegram. Автооновлення безпеки: `sudo apt install -y unattended-upgrades && sudo dpkg-reconfigure -plow unattended-upgrades` (відповідь **Yes**); у `/etc/apt/apt.conf.d/20auto-upgrades` мають бути два рядки з `"1"`. Оновлення ядра потребують перезавантаження, яке автоматично не робиться: час від часу перевіряйте `ls /var/run/reboot-required`. Не запускайте `do-release-upgrade`: 24.04 підтримується довго, а перехід на нову версію на 512 МіБ зайвий ризик.

### 3. Docker

За офіційною інструкцією Docker для Ubuntu (звірте її на https://docs.docker.com/engine/install/ubuntu/):

```bash
sudo apt update && sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker deploy      # діє після нового входу (exit і ssh знову)
```

Ротація журналу, щоб він не заповнив диск (діє на нові контейнери, тож зробіть це до першого запуску):

```bash
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
EOF

```

Група `docker` фактично дорівнює `root`: тримайте вхід лише за ключем і лише для `deploy`.

### 4. Azure Key Vault для сервера

Загальний опис див. «Azure Key Vault». На практиці:

1. **Окреме сховище** для JobWatcher (модель доступу **Azure RBAC**). Роль «Key Vault Secrets User» дається на рівні сховища й дає читання **усіх** його секретів, тому в спільному сховищі витік перепустки з сервера відкрив би й чужі секрети. Окреме сховище майже нічого не коштує (плата за операції).
2. Собі дайте роль **Key Vault Secrets Officer** на цьому сховищі: у режимі RBAC навіть власник підписки без неї не може створювати секрети.
3. Секрети: `JobWatcher--Telegram--BotToken`, `JobWatcher--Telegram--ChatId` і, якщо вмикаєте Jooble, `JobWatcher--Sources--Jooble--ApiKey`. Імена мають збігатися символ у символ.
4. **Microsoft Entra ID → App registrations → New registration**: ім'я `jobwatcher-droplet`, **Single tenant**. Запишіть **Application (client) ID** і **Directory (tenant) ID** (вони не секретні).
5. У цього застосунку: **Certificates & secrets → New client secret**. Скопіюйте стовпець **Value** одразу: Azure показує його лише раз (**Secret ID** не підходить). Секрет має строк дії: поставте нагадування в календарі, після закінчення строку сервіс не зможе прочитати сховище й не стартує.
6. У сховищі: **Access control (IAM) → Add role assignment → Key Vault Secrets User** → вибрати `jobwatcher-droplet` (його знаходить лише пошук за назвою).

Токен бота можна замінити (в @BotFather `/revoke`) під час переходу на сервер і вписати новий у секрет.

### 5. Образ

Mac на Apple Silicon (arm64), а Droplet x86 (amd64), тож образ збирайте під amd64 і передавайте на сервер напряму (збирати .NET на самому Droplet із 512 МіБ не варто):

```bash
docker buildx build --platform linux/amd64 -t jobwatcher:amd64 --load .
docker save jobwatcher:amd64 | gzip | ssh -i ~/.ssh/jobwatcher_digitalocean deploy@<IP-адреса> 'gunzip | docker load'
```

Етап збірки в Dockerfile запускається нативно (`--platform=$BUILDPLATFORM`): це швидко і без емуляції, а результат портативний (у `runtimes/` лежать нативні бібліотеки SQLite для всіх платформ). Передача займає кілька хвилин: образ у стисненому вигляді близько 40 МБ.

### 6. Налаштування й запуск

На сервері створіть файл `~/jobwatcher.env` з доступом до сховища. Секрет клієнта вводьте через `read -s`, щоб він не потрапив в історію команд. **`read` виконуйте окремо:** якщо вставити весь блок разом, наступні рядки «з'їсть» `read`.

```bash
umask 077
read -rsp 'Client secret: ' AZ_SECRET; echo        # вставте Value, Enter
printf 'KeyVault__VaultUri=%s\nAZURE_TENANT_ID=%s\nAZURE_CLIENT_ID=%s\nAZURE_CLIENT_SECRET=%s\n' \
  'https://<name>.vault.azure.net/' '<tenant id>' '<client id>' "$AZ_SECRET" > ~/jobwatcher.env
unset AZ_SECRET
sed 's/\(AZURE_CLIENT_SECRET=\).*/\1***/' ~/jobwatcher.env     # перевірка, секрет замасковано
```

Файл `appsettings.Development.json` в образ не потрапляє (його виключає `.dockerignore`), тож **ваші локальні відмінності** від типових значень треба повторити тут, дописавши в той самий файл (обов'язково `>>`). Приклад: Jooble увімкнено з українською адресою та розширений список регіонів віддаленої роботи:

```bash
cat >> ~/jobwatcher.env <<'EOF'
JobWatcher__Sources__Jooble__Enabled=true
JobWatcher__Sources__Jooble__BaseUrl=https://ua.jooble.org/api
JobWatcher__Profile__AllowedRemoteRegions__0=Ukraine
JobWatcher__Profile__AllowedRemoteRegions__1=Europe
JobWatcher__Profile__AllowedRemoteRegions__2=EU
JobWatcher__Profile__AllowedRemoteRegions__3=Worldwide
JobWatcher__Profile__AllowedRemoteRegions__4=US
JobWatcher__Profile__AllowedRemoteRegions__5=UK
EOF
```

**Перенесення бази `seen.db`** (якщо сервіс уже працював локально). Спершу переконайтеся, що локальний сервіс зупинено, і не запускайте його знову з тим самим токеном. Скопіюйте файл і покладіть у том з правами користувача 1654:

```bash
# на Mac:
scp -i ~/.ssh/jobwatcher_digitalocean <шлях до>/data/seen.db deploy@<IP-адреса>:/home/deploy/seen.db
# на сервері:
docker run --rm -u 0 --entrypoint sh -v jobwatcher-data:/app/data -v /home/deploy/seen.db:/in/seen.db:ro jobwatcher:amd64 \
  -c 'cp /in/seen.db /app/data/seen.db && chown -R 1654:1654 /app/data && ls -ln /app/data'
```

Без цього сервіс пройде «мовчазний перший запуск», і все, що з'явилося за час переходу, до вас не дійде. З перенесеною базою навпаки: вакансії, що з'явилися, поки сервіс не працював, прийдуть у перший цикл разом (це нормально).

Запуск:

```bash
docker run -d --name jobwatcher --restart unless-stopped \
  --env-file ~/jobwatcher.env -v jobwatcher-data:/app/data jobwatcher:amd64
docker logs -f jobwatcher        # Ctrl+C виходить, сервіс лишається
```

У журналі має бути `Читаю секрети з Azure Key Vault…` і підсумки циклу по кожному джерелу.

### 7. Повсякденні дії

- **Змінили секрет у Key Vault:** `docker restart jobwatcher` (секрети читаються на старті).
- **Змінили `~/jobwatcher.env`:** `docker restart` **не** перечитує файл змінних. Перестворіть контейнер: `docker rm -f jobwatcher`, потім той самий `docker run` (том із `seen.db` лишається).
- **Оновили код:** зберіть образ і передайте його (розділ 5), далі `docker rm -f jobwatcher` і `docker run` як вище.
- **Пам'ять і CPU:** `docker stats --no-stream jobwatcher`.
- **Сповіщення про простій:** сервіс не вміє повідомити про власну зупинку (див. «Перенесення в хмару»). Увімкніть сповіщення DigitalOcean про простій чи високе навантаження.
- **Резервні копії:** єдині дані, які варто берегти, це `seen.db`. Автоматичні копії DigitalOcean платні (за розміром відновлюваних даних) і необов'язкові: без копії найгірший наслідок це «мовчазний перший запуск».

### 8. Що трапляється на практиці

- **`Telegram sendMessage failed with HTTP 400: Bad Request: chat not found`.** Токен прийнято, але Telegram не знаходить чат. Найчастіше chat id у сховищі не той (одруківка, зайвий пробіл) або токен належить іншому боту, ніж той, у якому ви натискали **Start**. Виправте секрет і перезапустіть контейнер. Вакансії не губляться: вони повторюватимуться щоцикл, доки Telegram не прийме.
- **`Fetching DOU failed ... 403 (Forbidden)` лише на сервері.** З адреси дата-центру DigitalOcean DOU відповіла 403, тоді як із домашньої адреси стрічка читалася (200). Це схоже на свідому відмову, а умови DOU (п. 2.5) забороняють автоматизований доступ без згоди. Не обходьте її проксі чи підміною User-Agent. Вимкніть джерело (`JobWatcher__Sources__Dou__Enabled=false` у `~/jobwatcher.env` і перестворення контейнера) або напишіть адміністрації DOU (див. «DOU»).
- **Не вдається розшифрувати SSH-ключ** (`Bad passphrase` кілька разів поспіль): найчастіше не та розкладка клавіатури чи Caps Lock під час невидимого введення. Якщо фразу втрачено, створіть новий ключ і допишіть його відкритий рядок у `/home/deploy/.ssh/authorized_keys` із сесії, що ще відкрита.

### 9. Автоматичний деплой (GitHub Actions)

Після розділів вище оновлення сервера можна віддати пайплайну `.github/workflows/cd.yml` (за зразком `backend.yml` з qbeauty-ua). На кожен `push` у `main` (та вручну через **Run workflow**) він робить три кроки:

1. **Test:** `dotnet restore`, `build`, `test` усього рішення. На pull request виконується лише цей крок.
2. **Build & Push:** збирає образ під `linux/amd64` і пушить у GHCR (`ghcr.io/<власник>/<репозиторій>`) з тегом `sha-<7 символів коміту>` і `latest`.
3. **Deploy:** по SSH запускає на Droplet скрипт `deploy/deploy.sh`, який завантажує саме цей тег, перестворює контейнер із тим самим env-файлом і томом, чекає рядок `Application started` і, якщо контейнер не піднявся, повертає попередній образ (крок завершується помилкою).

Токен для завантаження образу на сервері не зберігається: пайплайн передає свій тимчасовий `GITHUB_TOKEN` у скрипт через stdin, скрипт виходить із реєстру після завантаження, а токен перестає діяти разом із завершенням запуску.

**Разове налаштування.**

1. **Окремий ключ для CI** (на Mac; без парольної фрази, бо CI не може її ввести, натомість ключ на сервері дозволяє одну дію):

   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/jobwatcher_ci -N "" -C "jobwatcher github actions"
   ```

2. **Скрипт і обмежений ключ на сервері.** Скопіюйте скрипт, потім на сервері зробіть його виконуваним і дозвольте CI-ключу виконувати **лише його**:

   ```bash
   # на Mac:
   scp -i ~/.ssh/jobwatcher_digitalocean deploy/deploy.sh deploy@<IP-адреса>:/home/deploy/deploy.sh
   echo "restrict,command=\"/home/deploy/deploy.sh\" $(cat ~/.ssh/jobwatcher_ci.pub)"   # виведе рядок, скопіюйте його
   # на сервері:
   chmod 700 /home/deploy/deploy.sh
   echo '<скопійований рядок>' >> ~/.ssh/authorized_keys
   ```

   `restrict,command=…` означає: цим ключем не можна відкрити термінал, лише виконати `deploy.sh`. Скрипт приймає тільки образ `ghcr.io/sqvlen/jobwatcher:<тег>` (власник і назва записані в `deploy.sh`; змініть їх, якщо репозиторій перенесуть). Не дозволяйте CI перезаписувати цей файл: інакше обмеження втрачає сенс.

3. **Відбиток сервера** для `known_hosts`, щоб пайплайн не довіряв першій-ліпшій відповіді. На Mac виведіть рядок і порівняйте його відбиток зі справжнім відбитком сервера:

   ```bash
   ssh-keyscan -t ed25519 <IP-адреса>                                    # цей рядок піде в секрет DEPLOY_KNOWN_HOSTS
   ssh-keyscan -t ed25519 <IP-адреса> | ssh-keygen -lf -                 # відбиток із мережі
   ssh -i ~/.ssh/jobwatcher_digitalocean deploy@<IP-адреса> 'ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub'   # справжній відбиток: має збігатися
   ```

4. **Секрети в GitHub.** Репозиторій → **Settings → Secrets and variables → Actions → New repository secret** (або в середовищі `production`: **Settings → Environments**, де можна ще й вимагати схвалення перед деплоєм):

   | Секрет | Значення |
   |---|---|
   | `DEPLOY_HOST` | IP-адреса Droplet |
   | `DEPLOY_USER` | `deploy` |
   | `DEPLOY_SSH_KEY` | повний вміст приватного `~/.ssh/jobwatcher_ci` (з рядками `BEGIN` і `END`) |
   | `DEPLOY_KNOWN_HOSTS` | рядок, який вивела `ssh-keyscan` |

5. **Перший запуск:** вкладка **Actions → CD → Run workflow** або `push` у `main`. Перший деплой замінить контейнер, запущений вручну, на образ із GHCR; env-файл і том із `seen.db` лишаються. Перевірте на сервері: `docker ps` і `docker logs jobwatcher`.

**Що пайплайн не чіпає.** Секрети (Key Vault) і налаштування (`~/jobwatcher.env`) лишаються на сервері й змінюються так, як у розділі 7: пайплайн оновлює лише образ. Дані (`seen.db`) живуть у томі й від деплою не залежать.

**Відкат.** Тег кожного деплою це `sha-…` конкретного коміту, тож повернутися можна запуском **Run workflow** на старому коміті або вручну на сервері: `docker rm -f jobwatcher`, потім `docker run …` з потрібним тегом (команда з розділу 6). Образи старші за 7 днів, які не використовуються, скрипт прибирає сам.

**Застереження.** Хто може змінити `cd.yml` у `main`, може змінити, що виконується в пайплайні, тому захистіть гілку `main` (обов'язковий pull request, схвалення) і не давайте запис у репозиторій стороннім. CI-ключ обмежений однією командою, але він усе ж дозволяє розгорнути будь-який образ вашого пакета в GHCR.

## Що ще приходить у Telegram

Крім вакансій, сервіс може надіслати службові повідомлення. Їх небагато, і вони не повторюються щоцикла.

- **⚠️ Джерело X не відповідає (N невдалих спроб поспіль)**: джерело не вдалося прочитати `FailureAlertThreshold` циклів поспіль (типово 3). Приходить один раз на збій. Коли джерело знову відповість, лічильник скидається, і наступний збій сповістить знову. Лічильники живуть у пам'яті: після перезапуску починаються з нуля.
- **ℹ️ Джерело X не підключено: ...**: ввімкнено джерело, до якого немає доступу (зараз це лише LinkedIn). Приходить **раз на запуск процесу**: після кожного перезапуску сервісу прийде знову.
- **⚠️ Не вдалося надіслати вакансію ... (компанія): посилання**: Telegram тричі не прийняв саме це повідомлення (або саме для цієї вакансії тричі не вдалося скласти текст повідомлення). Сервіс повідомляє про це й іде далі, щоб одна вакансія не блокувала решту. Посилання в повідомленні, відкрийте вакансію вручну.
- **⚠️ Цикл перевірки не вдається (N разів поспіль): ТипПомилки. Подробиці в журналі сервісу.**: увесь цикл перевірки завершувався помилкою `FailureAlertThreshold` разів поспіль (типово 3), тобто вакансії зараз не надходять. Найчастіша причина: не вдається записати базу `seen.db`. Приходить один раз на серію збоїв; якщо Telegram його не прийняв, сервіс спробує ще раз після наступного невдалого циклу. Після першого вдалого циклу лічильник скидається, і наступна серія сповістить знову. У повідомленні лише назва типу помилки, без її тексту, тож жоден секрет туди не потрапляє. Що перевірити: журнал сервісу (`Watch cycle failed` із повним текстом помилки); права на запис у каталог даних (у Docker том `/app/data` має бути доступний на запис користувачу з id **1654**, див. «Попередження про каталог замість тома»); вільне місце на диску.

Якщо Telegram недоступний, цикл просто зупиняється, а ненадіслане повторюється в наступному циклі: вакансію позначено побаченою лише після того, як Telegram її прийняв, тож нічого не губиться.

### Що показує журнал

Службова інформація йде не лише в Telegram, а й у журнал: його видно в консолі, де запущено сервіс (у Docker: `docker logs -f jobwatcher`). Щоб побачити, що сервіс живий і скільки вакансій він прочитав, достатньо рядків рівня `info`. У журналі немає токена, ключів чи адрес із ними.

**`First run of …`: перший запуск джерела.**

```
info: JobWatcher.Watching.WatchCycle[0]
      First run of DOU: 25 existing vacancies marked as seen
```

Джерело відповіло вперше: 25 вакансій, що вже висять на сайті, мовчки записано як «побачені», у Telegram нічого не піде. Це єдиний рядок із числами для цього джерела в цьому циклі. Поки джерело не віддало жодної придатної вакансії, воно лишається в режимі «перший запуск», і замість цього рядка в кожному циклі пишеться підсумок із нулями (див. нижче), тож порожнє джерело не виглядає як завислий сервіс.

**Підсумок циклу.** У кожному циклі (кожні `PollIntervalMinutes`) про кожне джерело, що відповіло, пишеться один рядок (крім циклу, у якому джерело вперше віддало вакансії, див. вище):

```
info: JobWatcher.Watching.WatchCycle[0]
      DOU: fetched 25, new 3, matching the profile 2, sent 2, held back 0
```

- `fetched`: скільки вакансій віддало джерело в цьому циклі (усі, ще до перевірок).
- `new`: скільки з них ще не позначені як «побачені» (вакансії з порожніми полями та повтори не рахуються; вакансія, яку не вдалося надіслати чи яку утримано через ліміт, лишається непобаченою й рахується знову в наступних циклах).
- `matching the profile`: скільки з нових підійшло під профіль (технологія, досвід, місто чи віддалена робота та, якщо задано `MinSalary`, мінімальна зарплата).
- `sent`: скільки повідомлень Telegram справді прийняв у цьому циклі.
- `held back`: скільки підхожих вакансій не надіслано в цьому циклі, бо вичерпано `MaxMessagesPerCycle`. Вони не губляться й підуть у наступних циклах. Без ліміту завжди `0`. Ліміт спільний для всіх джерел за цикл: джерело, яке йде пізніше, може показати `sent 0, held back 2`, бо бюджет уже витратило попереднє.

Приклад. Рядок вище читається так: DOU віддала 25 вакансій, 3 з них нові, 2 із цих трьох підходять під профіль, обидві надіслано, а третю нову просто запам'ятано без повідомлення. Рядок `fetched 25, new 0, matching the profile 0, sent 0, held back 0` означає, що джерело працює, а нового просто немає: це не збій. А `fetched 25, new 5, matching the profile 5, sent 2, held back 3` (за `MaxMessagesPerCycle=2`) означає, що п'ять нових підходять, два повідомлення надіслано, три підуть у наступних циклах.

Тож `matching the profile` не завжди дорівнює `sent` плюс `held back`. Підхожа вакансія, яку не вдалося надіслати (Telegram відмовив або не вдалося скласти текст повідомлення), і вакансії, до яких цикл не дійшов через зупинку, не рахуються ні в `sent`, ні в `held back`; вони повернуться в наступних циклах. Так само з вакансією, про невдачу якої надіслано службове повідомлення: вона не рахується в `sent`, а далі її вже не повторюють.

Якщо Telegram відмовив посередині циклу, підсумок усе одно з'являється з тим, що встигло піти (наприклад, `sent 1`), а слідом іде попередження про зупинку циклу.

Рядок `fetched 0, new 0, matching the profile 0, sent 0, held back 0` означає, що джерело відповіло, але не віддало жодної вакансії. Якщо ж `fetched` більше нуля, а `new` нуль, причиною може бути й те, що всі віддані вакансії непридатні (порожні поля, повтори, чужа мітка джерела): тоді перед підсумком стоїть рядок `Ignored … vacancies …`. Якщо нулі тривають довго, перевірте джерело: зміну адреси чи формату стрічки, для Jooble ще й ключ та домен.

Підсумку немає в циклі, коли джерело вперше віддало вакансії (там `First run of …`), коли джерело не підключене (`Source … is not connected`) і коли його не вдалося прочитати (там попередження `Fetching … failed`).

**Jooble: «no request this time».** Безкоштовний ключ Jooble має обмежену квоту, тому справжній запит робиться не частіше ніж раз на `MinFetchIntervalMinutes` (типово 720 хвилин). У циклах між ними пишеться:

```
info: JobWatcher.Sources.JoobleSource[0]
      Jooble: no request this time, the next one is due after 2026-10-22T20:00:00.0000000Z (MinFetchIntervalMinutes=720)
```

Це норма: запиту не було, квоту збережено, а після `due after` стоїть час (UTC), раніше за який нового запиту не буде. Поруч підсумок Jooble у ці цикли показує `fetched 0`, бо без запиту вакансій немає. Якщо остання справжня вибірка Jooble закінчилася помилкою, то в циклах до наступного запиту замість цього рядка пишеться попередження `Fetching Jooble failed` (текст помилки в ньому називає час наступної спроби; див. [docs/sources/jooble.md](docs/sources/jooble.md)).

**Djinni: «details read».** Коли в стрічці Djinni є нові вакансії, перед підсумком Djinni пишеться, скільки їхніх сторінок прочитано:

```
info: JobWatcher.Watching.WatchCycle[0]
      Djinni: details read for 3 of 5 new vacancies, deferred 0
```

Тут з 5 нових вакансій сторінки трьох прочитано, а дві пішли далі без подробиць (про кожну перед цим є попередження `Could not read the details of Djinni vacancy <номер>: <тип помилки>: <текст>`). Вакансія, сторінку якої прочитано в одному з попередніх циклів (вона ще чекала надсилання), рахується як прочитана без нового запиту. `deferred` це нові вакансії понад `MaxPagesPerCycle`: їх у цьому циклі не перевіряли й не запам'ятовували, вони прийдуть у наступних. `new` у підсумку Djinni рахує лише вакансії, які в цьому циклі пішли на фільтр, без відкладених. Якщо нові вакансії були, а не прочитано жодної сторінки, цей рядок пишеться як попередження (`warn:`): найімовірніше, Djinni змінила розмітку сторінок, і вакансії приходять без компанії й зарплати.

**Попередження й помилки.** Рядки `warn:` і `fail:` означають проблему, на яку варто глянути: наприклад, `Fetching DOU failed` (джерело не відповіло), `Telegram did not accept vacancy …` або `Telegram is not accepting messages` (Telegram не прийняв повідомлення, повторимо в наступному циклі), `Watch cycle failed` (збій усього циклу, найчастіше база `seen.db`). Поки в журналі лише `info:`, усе гаразд.

## Відомі обмеження

- **Дублікати між сайтами.** Дедуплікація працює лише в межах одного джерела. Та сама вакансія з двох сайтів (наприклад, вакансія з Jooble, яка є й на DOU) може прийти двічі.
- **Перезапуск після змін.** Увімкнені джерела й налаштування читаються на старті: після зміни `Enabled`, ключів чи профілю перезапустіть сервіс.
- **Вимог може не бути.** Блок `📋 Вимоги:` показується, лише коли в описі є чіткий розділ вимог із пунктами. Jooble віддає тільки уривок опису, тож для нього вимог зазвичай немає.
- **Дані Djinni залежать від сторінки вакансії.** Стрічка Djinni не має компанії, зарплати й місця; їх дає сторінка нової вакансії. Якщо її не вдалося прочитати, вакансія приходить з «не вказано» і за місцем, форматом та зарплатою не відсіюється, див. «Джерела».
- **Без рейтингу компаній.** Див. «Джерела».
- **Один користувач, один чат, один профіль.**
- **Каталог даних відносно поточного каталогу.** `appsettings.json` шукається поруч із `JobWatcher.dll`, тож програму можна запускати з будь-якого каталогу. А типовий каталог даних `./data` відносний до **поточного (робочого) каталогу**: запускаючи зібраний `JobWatcher.dll` вручну, запускайте його щоразу з того самого каталогу або задайте `JobWatcher__DataDir` абсолютним шляхом, інакше з'явиться нова порожня `seen.db` і знову мовчазний «перший запуск». Docker (робочий каталог `/app`, `JobWatcher__DataDir=/app/data`) це вже враховує.
